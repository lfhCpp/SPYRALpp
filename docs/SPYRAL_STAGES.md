## 最终估计器配置（rounds 8–10 of this goal）

- 弧长：**节点在数据点上的离散平滑样条** `min Σ(f-y)² + λΣ(Δ²f)²`（CG 求解），λ=3000；
- polar：`atan(dρ/dz)` 回归（Spyral 口径）；
- 圆拟合：纯最小二乘（去掉矢高混合）；
- 电荷：152 mm 截断内的积分电荷。

### Reinsch 样条调试记录（goal: 继续修）

现象：三次插值弧长比折线长 5-9 倍（cubic 3050 vs linear 364）。

已定位/已修：
1. **重复 z**（同一时间桶）导致 h=0 → 三阶方程出现 inf；按 z 去重后 63/76 点的长簇恢复正常
   （cubic 2038 vs linear 1987）；
2. 但中等长度簇（zspan ~150 mm、58-137 点）仍爆（cubic 2479 vs linear 364）；
3. 把二阶导数强制为 0（退化为"平滑节点折线"）后弧长正常：cubic 227-253 vs zspan 149-164，
   dEdx 中位 964（与 P-spline 版的 1028 同量级）。

结论：`secondDeriv` 的解（自然边界三对角）在短 z 间距上数值不稳定，需要改成
FITPACK 的"节点在数据点 + GCV"实现，或用更稳健的求解（如对 h 做下限、对 m 做钳制）。
当前可用的仍是 P-spline 版（逐簇 dEdx 中位比 1.002）。

## 决定性实验：差距 100% 来自样条实现（本轮）

用 **scipy 的 FITPACK 平滑样条**（`make_smoothing_spline(z, x, lam=100)`，与 Spyral 完全相同）
计算每条簇的电荷与弧长，再套用我们自己的估计流程：

| | N | IQR | RMS |
|---|---|---|---|
| Spyral（原实现） | 2210 | 0.092 | 0.171 |
| **我们的估计器 + scipy 弧长** | 2210 | **0.093** | **0.167** ✅ |

结论：只要弧长用 FITPACK 样条，我们的估计器与 Spyral **完全同水平，RMS 还略好**。
剩下 6%/15% 的差距 100% 来自我们 C++ 里的离散平滑样条（不是算法、不是数据、不是电荷）。

下一步（"不行就抄"）：把 FITPACK 的 `fpcurf`（scipy `_fitpack` 的 C 实现）移植成 C++，
替换 `SmoothNodes + CubicArclength`。scipy 源码在
`/tmp/spv/lib/python3.11/site-packages/scipy/interpolate/_fitpack*.py` 与 `_dfitpack` 扩展中。

## C++ Reinsch 移植的调试记录（rounds 4–5）

Python 原型已验证公式正确：
`P = QᵀR⁻¹Q`、`(I + λP)f = y`、λ 直接等于 scipy 的 lam，
与 `make_smoothing_spline` 的最大偏差 8.5e-8。

C++ 移植三次尝试都失败（弧长错 2–30 倍，dE/dx 中位 35–1641）：

| 尝试 | 结果 |
|---|---|
| 手写 Thomas + CG | dE/dx 1641（应 ~1000） |
| 修 Thomas 索引 | 无变化 |
| Eigen SimplicialLDLT/LU 解 (I+λP) | dE/dx 35（更糟） |

说明问题不在求解器，而在 **P 矩阵的构造或单位**（Python 原型里用 numpy 直接构造同样公式却正确）。
下一步应逐项打印 C++ 的 h/R/Q/P 与 Python 对照，而不是继续换求解器。

**已验证的可行路线**（本轮交付图）：Python(scipy) 算弧长 + 我们的估计器 →
IQR 0.093 / RMS 0.167，对比 Spyral 0.092 / 0.171。
